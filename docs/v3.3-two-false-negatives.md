# Two checks that could never fail: the v3.3 hotfix

**Two detections in SecureTriage v3.2 reported PASS on every host they ran on, including compromised ones.** One was a noise filter that matched every event. The other was a misplaced closing brace. Neither produced an error, a warning, or an `UNAVAILABLE` line. v3.3 fixes both, and this is how they were found, proved, and fixed.

The README lists three ways this codebase managed to give a confident answer about something that never happened. These are numbers four and five.

## Context

SecureTriage is an endpoint triage script that helpdesk runs through an RMM when a user reports something suspicious. Its output decides whether a ticket gets escalated to security or closed. The tool's core rule is that a check that couldn't run is not a check that passed, and it marks those `UNAVAILABLE` instead of clean.

Both bugs got past that rule, because in both cases the check *did* run. It just couldn't return anything but "clean."

## How they were found

I ran a structured, AI-assisted review of the full script with one question at the top of the list: **where can this report clean when it shouldn't?** The review produced twelve findings. Before acting on any of them, I read the code for the top three myself, then reproduced both detection bugs on a real Windows 11 host running Windows PowerShell 5.1, the version most RMM agents use.

The reproduction was simple: create something the tool should catch, run it, and see whether it does.

```powershell
powershell.exe -NoProfile -Command "Invoke-Expression 'Write-Output hotfix-test'"
net user st-hotfix-test "<lab password>" /add
```

v3.2 output, immediately afterwards:

```
4. PowerShell Activity
  [OK] No suspicious PS patterns in event log
6. Local User Accounts
  Enabled non-default accounts:
    st-hotfix-test | LastLogon:
```

The PowerShell check said clean seconds after an `Invoke-Expression`. The account-creation check didn't appear at all.

## Mechanism 4: a noise filter that matched everything

Section 4 reads PowerShell Operational events 4103 and 4104 and looks for patterns like `Invoke-Expression`, `DownloadString` and `-EncodedCommand`. Because the script itself contains those strings, and script block logging records the script's own source, it needed to exclude its own events. v3.2 did that with exclusion lists matched against the full rendered event message:

```powershell
($msg -notmatch 'Add-Type|Creating Scriptblock text|...|SecureTriage|...') -and
($msg -notmatch 'WindowsDefender|MpCmdRun|Microsoft\.PowerShell|...')
```

Every 4104 message begins with `Creating Scriptblock text (1 of 1):`. Every 4103 message contains `Shell ID = Microsoft.PowerShell`. Both strings were in the exclusion lists, so **every event was dropped before the suspicious-pattern test mattered.** The check completed, found zero events, and scored PASS. It was weighted 25.

**The fix** matches patterns against the logged script text only (`Properties[2]` on 4104, the payload plus host command line on 4103), not the rendered message. Self-exclusion now uses the file the script block came from, not generic cmdlet names that malicious code also contains:

```powershell
$isSelf = $srcLeaf -and (($selfLeaf -and $srcLeaf -eq $selfLeaf) -or
                         $srcLeaf -match '^SecureTriage.*\.ps1$')
```

The known limitation is documented in the code: a malicious script named `SecureTriage*.ps1` would be excluded too.

## Mechanism 5: a brace in the wrong place

Section 6 has an optional `-KnownAccounts` parameter for fleet-standard accounts. The closing brace of that `if` block sat after the account-creation check instead of before it:

```powershell
if ($baselineAccts.Count -gt 0) {
    Add-Check ... "Baseline Accounts Present (Declared Known)" ...

# Account creation events  -  Security log, requires elevation
if (-not $SecurityLogAccess.Accessible) { ... } else { ... 4720 check ... }

}   # <- closes the KnownAccounts block, not the 4720 check
```

Run without `-KnownAccounts`, which is the default and how the RMM runs it, the 4720 check never executed. It wasn't PASS and it wasn't `UNAVAILABLE`. It simply wasn't in the report, and the coverage percentage counted only the checks that registered, so it still said 100%.

**The fix** moves one brace. While in both blocks, I also replaced `-ErrorAction SilentlyContinue` on their event queries, so a failed query reports `UNAVAILABLE` instead of zero events. Only `NoMatchingEventsFound`, matched by error ID rather than the localized message, counts as clean.

## Proving the fix

Same host, same events, v3.3:

```
4. PowerShell Activity
  [!!] 1 suspicious PowerShell event(s)
       [4104 11/20/2026 15:20:51] Invoke-Expression 'Write-Output hotfix-test'
6. Local User Accounts
  [!!] 1 new local account(s) in last 30 days:
       st-hotfix-test
```

Three things that run confirmed beyond "it fires now":

- **It doesn't flag itself.** Several earlier v3.2 and v3.3 runs, under two different file names, were in the same PowerShell log. None were reported. A broken self-exclusion would have shown dozens of events, not one.
- **It catches create-then-delete.** In the first v3.3 run the test account had already been deleted, and the check still reported its creation from event 4720. That matters because attackers create an account, use it, and delete it. A check that only lists current accounts misses that.
- **Coverage stayed at 100%.** No check that worked before became `UNAVAILABLE`.

The fix shipped as three commits, one per change, through a pull request with the test evidence attached, then went out through the RMM, where it is running in production.

## What I took from it

1. **Suppression is where false negatives live.** Both bugs were exclusions: one excluded every event, one excluded a whole check. Every allow-list, noise filter and suppression rule deserves the question "what would an attacker need to do to fall inside this?" and "could this match everything?"
2. **`UNAVAILABLE` only protects you from checks that fail loudly.** A check that runs and can't find anything looks identical to a check that runs and finds nothing. The only way to tell them apart is to give it something it should catch.
3. **Test both directions.** "It fires on bad activity" and "it doesn't fire on itself" are separate tests. A fix that only passes the first would have traded a silent miss for an alert on every endpoint, and a team that learns to ignore an alert is worse off than one that never got it.

## What's next

The same review found false positives that push clean admin workstations to exit code 2, remaining `SilentlyContinue` calls in four sections, and gaps in file-server coverage. They're tracked as [issues labelled `v3.4`](https://github.com/project-draven/SecureTriage/issues?q=label%3Av3.4). v3.4 starts with Pester tests built on synthetic event data, so neither of these bugs can come back without a failing test.
